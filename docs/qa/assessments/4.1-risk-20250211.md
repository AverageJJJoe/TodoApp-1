## Detailed Risk Analysis

### BUS-001: Incorrect Cohort Assignment (HIGH RISK)

**Score:** 6 (High)  
**Probability:** Medium (2) - Could occur due to calculation errors, timezone issues, or week boundary edge cases  
**Impact:** High (3) - Direct revenue impact, customer dissatisfaction, potential refund requests

**Description:**
If cohort assignment logic incorrectly calculates weeks or assigns wrong cohort, users may:
- Receive incorrect pricing (free instead of paid, or wrong price point)
- Be charged incorrectly leading to refunds and reputation damage
- Experience paywall at wrong time (too early or too late)

**Affected Components:**
- `src/lib/cohortAssignment.ts` - Week calculation and assignment logic
- `src/stores/taskStore.ts` - Integration point 1
- `src/screens/OnboardingScreen.tsx` - Integration point 2
- `src/screens/SettingsScreen.tsx` - Integration point 3

**Detection Method:**
- Manual testing across week boundaries
- Database verification after signup
- Revenue reconciliation reports

**Mitigation Strategy:** Preventive
- **Actions:**
  1. Unit tests for `calculateWeeksSinceLaunch` with edge cases (day boundaries, timezone boundaries)
  2. Unit tests for `assignCohort` with all week ranges (1-3, 4-6, 7-8, 9+)
  3. Integration tests verifying cohort assignment in all three user creation paths
  4. Manual testing across week transitions (e.g., day 20→21, 41→42, 55→56)
  5. Idempotency check prevents overwriting (mitigates DATA-001)
  6. Clear logging in dev mode for troubleshooting
- **Testing Requirements:**
  - Unit tests: Week calculation for all boundary conditions
  - Integration tests: Full signup flow with cohort verification
  - Manual testing: Multiple signups across different week ranges
- **Residual Risk:** Low - With comprehensive testing, incorrect assignment becomes unlikely
- **Owner:** Development team
- **Timeline:** Before deployment

### DATA-001: Cohort Overwriting (MEDIUM RISK)

**Score:** 4 (Medium)  
**Probability:** Medium (2) - Could occur if cohort assignment runs multiple times on same user  
**Impact:** Medium (2) - User's cohort could be incorrectly changed, affecting pricing

**Description:**
If cohort assignment runs multiple times (e.g., user created in multiple places), could overwrite correct cohort assignment with incorrect one based on current week, not signup week.

**Affected Components:**
- All three integration points (taskStore, OnboardingScreen, SettingsScreen)
- User creation logic

**Mitigation Strategy:** Preventive (Already addressed in story)
- **Actions:**
  1. ✅ Idempotency check: Only assign if `cohort === 'free_launch'` (default)
  2. Query user record before assignment
  3. Skip assignment if cohort already set to non-default value
- **Testing Requirements:**
  - Test: Create user, assign cohort, then trigger user creation again - verify cohort not overwritten
  - Test: Verify all three integration points respect idempotency check
- **Residual Risk:** Low - Idempotency check prevents overwriting
- **Owner:** Development team
- **Timeline:** During implementation

### TECH-001: Week Calculation Error (MEDIUM RISK)

**Score:** 4 (Medium)  
**Probability:** Medium (2) - Timezone issues, off-by-one errors in day calculation, or rounding issues could occur  
**Impact:** Medium (2) - Incorrect week calculation leads to wrong cohort assignment

**Description:**
Week calculation logic could produce incorrect week number due to:
- Timezone conversion errors (launchDate vs current date in different timezones)
- Off-by-one errors in day-to-week conversion
- Rounding errors (should use `Math.floor`, not `Math.round`)
- Edge cases at week boundaries (e.g., exactly 21 days = week 3 or week 4?)

**Affected Components:**
- `calculateWeeksSinceLaunch` function
- `assignCohort` function (depends on week calculation)

**Mitigation Strategy:** Preventive
- **Actions:**
  1. Use UTC for all date calculations to avoid timezone issues
  2. Use `Math.floor` (not `Math.round`) for week calculation to ensure correct week boundaries
  3. Add unit tests for boundary conditions:
     - Day 0-6: Week 1
     - Day 7-13: Week 2
     - Day 14-20: Week 3
     - Day 21-27: Week 4 (first free_launch day)
     - Day 42-48: Week 7 (first early_freemium day)
     - Day 49-55: Week 8
     - Day 56+: Week 9 (paid_cohort_v1)
  4. Test timezone edge cases (ensure UTC handling)
- **Testing Requirements:**
  - Unit tests: Week calculation for all boundary days
  - Unit tests: Verify `Math.floor` behavior (e.g., day 20.9 should be week 2, not week 3)
- **Residual Risk:** Low - Comprehensive unit testing prevents calculation errors
- **Owner:** Development team
- **Timeline:** During implementation

### BUS-002: Unbalanced Random Split (LOW RISK)

**Score:** 2 (Low)  
**Probability:** Low (1) - Statistical variance could create temporary imbalance, but `Math.random()` should converge to 50/50 over time  
**Impact:** Medium (2) - Minor business impact if split is significantly unbalanced, but acceptable variance in small samples

**Description:**
Random split using `Math.random() < 0.5` for weeks 7-8 could create temporary imbalance. For small sample sizes, seeing 60/40 or 40/60 distribution is normal, but could be mistaken for a bug.

**Affected Components:**
- `assignCohort` function (weeks 7-8 logic)

**Mitigation Strategy:** Accept
- **Actions:**
  1. Document that some variance is expected with small sample sizes
  2. For testing: Create multiple test users to verify distribution (statistical sampling)
  3. Monitor actual distribution in production after launch
- **Testing Requirements:**
  - Integration test: Create 20+ test users in week 7-8 range, verify distribution is roughly 50/50 (allow ±30% variance for small samples)
- **Residual Risk:** Low - Statistical variance is acceptable, no mitigation needed beyond documentation
- **Owner:** Product/Development team
- **Timeline:** Monitoring post-deployment

### TECH-002: Environment Variable Not Configured (LOW RISK)

**Score:** 2 (Low)  
**Probability:** Low (1) - Well-documented in story, but could be missed in production deployment  
**Impact:** Medium (2) - Cohort assignment would fail or use default, affecting monetization

**Description:**
If `launchDate` is not configured in `app.json`, cohort assignment logic would fail or produce incorrect results. Default behavior (fallback) could assign all users to wrong cohort.

**Affected Components:**
- `app.json` configuration
- Cohort assignment function calls

**Mitigation Strategy:** Detective/Corrective
- **Actions:**
  1. Add runtime validation: Check if `launchDate` exists before assignment
  2. Add error logging if `launchDate` is missing
  3. Document in deployment checklist
  4. Add startup validation (optional enhancement)
- **Testing Requirements:**
  - Test: Missing `launchDate` should log error and use safe default or fail gracefully
- **Residual Risk:** Low - Runtime validation prevents silent failures
- **Owner:** Development/DevOps team
- **Timeline:** During implementation

### OPS-001: Silent Failure of Client-Side Assignment (LOW RISK)

**Score:** 2 (Low)  
**Probability:** Low (1) - Error handling is specified in story, but network issues or RLS failures could cause silent failures  
**Impact:** Medium (2) - Users stuck with default `'free_launch'` cohort, affecting revenue tracking and monetization

**Description:**
Client-side cohort assignment could fail silently if:
- Network request to Supabase fails
- RLS policy blocks update (unlikely, but possible)
- User update fails for any reason
- Error handling doesn't catch all failure modes

**Affected Components:**
- All three integration points
- Error handling logic

**Mitigation Strategy:** Detective (Story already includes error handling)
- **Actions:**
  1. ✅ Error handling specified: try/catch blocks with logging (Task 5)
  2. ✅ Graceful degradation: User still gets created with default cohort
  3. Add explicit error logging to help identify failures
  4. Future enhancement: Consider database trigger for automatic assignment (noted in story)
- **Testing Requirements:**
  - Test: Network failure should log error but not block user creation
  - Test: Verify error logging works correctly
- **Residual Risk:** Low-Medium - Error handling helps, but some failures may still go unnoticed
- **Owner:** Development team
- **Timeline:** During implementation
