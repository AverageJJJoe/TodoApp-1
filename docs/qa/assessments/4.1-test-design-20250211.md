# Test Design: Story 4.1 - Cohort Assignment on Signup

**Date:** 2025-02-11  
**Designer:** Quinn (Test Architect)  
**Story:** 4.1 - Cohort Assignment on Signup  
**Epic:** 4 - Monetization & Payments

---

## Test Strategy Overview

- **Total test scenarios:** 18
- **Unit tests:** 10 (56%)
- **Integration tests:** 6 (33%)
- **E2E tests:** 2 (11%)
- **Priority distribution:** P0: 8, P1: 7, P2: 3

**Test Strategy Rationale:**
- **Unit tests (56%):** Pure business logic (week calculation, cohort assignment) is ideal for unit testing - fast, isolated, comprehensive
- **Integration tests (33%):** Database operations and Supabase client integration require integration testing
- **E2E tests (11%):** Minimal E2E coverage - full signup flow verification sufficient for MVP

### AC2: Cohort Assignment Logic Implemented

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.1-UNIT-002 | Unit | P0 | Test `calculateWeeksSinceLaunch` - boundary days | Pure calculation logic |
| 4.1-UNIT-003 | Unit | P0 | Test `calculateWeeksSinceLaunch` - timezone handling | Pure calculation logic |
| 4.1-UNIT-004 | Unit | P0 | Test `assignCohort` - weeks 1-3 (fallback) | Pure business logic |
| 4.1-UNIT-005 | Unit | P0 | Test `assignCohort` - weeks 4-6 (free_launch) | Pure business logic |
| 4.1-UNIT-006 | Unit | P0 | Test `assignCohort` - weeks 7-8 (random split) | Pure business logic |
| 4.1-UNIT-007 | Unit | P0 | Test `assignCohort` - week 9+ (paid_cohort_v1) | Pure business logic |
| 4.1-UNIT-008 | Unit | P1 | Test random split distribution (statistical) | Pure business logic |
| 4.1-INT-002 | Integration | P0 | Test cohort assignment with Supabase update | Database integration |
| 4.1-INT-003 | Integration | P1 | Test environment variable loading (`launchDate`) | Configuration integration |

**4.1-UNIT-002: Week Calculation - Boundary Days (Unit, P0)**
- **Description:** Test `calculateWeeksSinceLaunch` for all week boundary days
- **Given:** Launch date = "2025-01-01T00:00:00Z"
- **When:** Calculate weeks for boundary days:
  - Day 0 (2025-01-01): Week 1
  - Day 6 (2025-01-07): Week 1
  - Day 7 (2025-01-08): Week 2
  - Day 13 (2025-01-14): Week 2
  - Day 14 (2025-01-15): Week 3
  - Day 20 (2025-01-21): Week 3
  - Day 21 (2025-01-22): Week 4 ✅ (first free_launch day)
  - Day 27 (2025-01-28): Week 4
  - Day 41 (2025-02-11): Week 6
  - Day 42 (2025-02-12): Week 7 ✅ (first early_freemium day)
  - Day 48 (2025-02-18): Week 7
  - Day 49 (2025-02-19): Week 8
  - Day 55 (2025-02-25): Week 8
  - Day 56 (2025-02-26): Week 9 ✅ (first paid_cohort_v1 day)
- **Then:** All calculations return correct week numbers
- **Justification:** Pure calculation logic, critical for correct cohort assignment

**4.1-UNIT-003: Week Calculation - Timezone Handling (Unit, P0)**
- **Description:** Verify week calculation uses UTC to avoid timezone issues
- **Given:** Launch date in UTC, current date in different timezone
- **When:** Calculate weeks
- **Then:** Calculation uses UTC for both dates, timezone differences don't affect result
- **Test Data:** Launch = "2025-01-01T00:00:00Z" (UTC), Current = various timezones converted to UTC
- **Justification:** Prevents timezone-related bugs in week calculation

**4.1-UNIT-004: Assign Cohort - Weeks 1-3 (Unit, P0)**
- **Description:** Test `assignCohort` for weeks 1-3 (fallback to free_launch)
- **Given:** weeksSinceLaunch = 1, 2, or 3
- **When:** Call `assignCohort(weeksSinceLaunch)`
- **Then:** Returns `{ cohort: 'free_launch', grandfatherStatus: false, trialExpiresAt: null, trialStartedAt: null }`
- **Justification:** Pure business logic, tests fallback behavior

**4.1-UNIT-005: Assign Cohort - Weeks 4-6 (Unit, P0)**
- **Description:** Test `assignCohort` for weeks 4-6 (free_launch with grandfather_status)
- **Given:** weeksSinceLaunch = 4, 5, or 6
- **When:** Call `assignCohort(weeksSinceLaunch)`
- **Then:** Returns `{ cohort: 'free_launch', grandfatherStatus: true, trialExpiresAt: null, trialStartedAt: null }`
- **Justification:** Pure business logic, critical for revenue (grandfathered users)

**4.1-UNIT-006: Assign Cohort - Weeks 7-8 (Unit, P0)**
- **Description:** Test `assignCohort` for weeks 7-8 (random split between 2.99 and 4.99)
- **Given:** weeksSinceLaunch = 7 or 8
- **When:** Call `assignCohort(weeksSinceLaunch)` multiple times (mock Math.random)
- **Then:** 
  - Returns either `{ cohort: 'early_freemium_2.99', ... }` or `{ cohort: 'early_freemium_4.99', ... }`
  - `grandfatherStatus: false`
  - `trialStartedAt` and `trialExpiresAt` are set (30 days apart)
- **Test Data:** Mock `Math.random()` to test both outcomes
- **Justification:** Pure business logic, tests random split and trial date calculation

**4.1-UNIT-007: Assign Cohort - Week 9+ (Unit, P0)**
- **Description:** Test `assignCohort` for week 9+ (paid_cohort_v1)
- **Given:** weeksSinceLaunch = 9, 10, or higher
- **When:** Call `assignCohort(weeksSinceLaunch)`
- **Then:** Returns `{ cohort: 'paid_cohort_v1', grandfatherStatus: false, trialExpiresAt: Date + 30 days, trialStartedAt: Date }`
- **Justification:** Pure business logic, tests standard pricing cohort

**4.1-UNIT-008: Random Split Distribution (Unit, P1)**
- **Description:** Test statistical distribution of random split (weeks 7-8)
- **Given:** weeksSinceLaunch = 7
- **When:** Call `assignCohort` 100 times with real Math.random()
- **Then:** Distribution is roughly 50/50 (±20% variance acceptable for sample size)
  - Count of `'early_freemium_2.99'` should be 40-60 out of 100
  - Count of `'early_freemium_4.99'` should be 40-60 out of 100
- **Justification:** Verifies random split works correctly (statistical test)

**4.1-INT-002: Cohort Assignment with Database Update (Integration, P0)**
- **Description:** Test complete flow: calculate weeks → assign cohort → update Supabase
- **Given:** Test user in Supabase, `launchDate` configured
- **When:** Call cohort assignment function, then update user record
- **Then:** 
  - User record updated with correct `cohort`, `grandfather_status`, `trial_started_at`, `trial_expires_at`
  - Database query confirms values match expected cohort assignment
- **Test Data:** Test user with `cohort = 'free_launch'` (default)
- **Justification:** Requires Supabase client integration, tests end-to-end assignment flow

**4.1-INT-003: Environment Variable Loading (Integration, P1)**
- **Description:** Test `launchDate` is correctly loaded from `app.json` via Expo Constants
- **Given:** `app.json` with `launchDate` in `extra` field
- **When:** Access via `Constants.expoConfig?.extra?.launchDate`
- **Then:** Value is correctly retrieved as ISO date string
- **Test Data:** Configure `app.json` with test `launchDate`
- **Justification:** Configuration loading requires Expo Constants integration

### AC3: Cohort Assignment Runs Automatically

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.1-INT-004 | Integration | P0 | Test cohort assignment in taskStore user creation | Multi-component integration |
| 4.1-INT-005 | Integration | P0 | Test cohort assignment in OnboardingScreen user creation | Multi-component integration |
| 4.1-INT-006 | Integration | P0 | Test cohort assignment in SettingsScreen user creation | Multi-component integration |
| 4.1-INT-007 | Integration | P1 | Test idempotency check (prevent overwriting) | Multi-component integration |
| 4.1-E2E-001 | E2E | P0 | Test complete signup flow with cohort assignment | Critical user journey |

**4.1-INT-004: Cohort Assignment - TaskStore Integration (Integration, P0)**
- **Description:** Test cohort assignment when user is created via taskStore
- **Given:** New user (no user record exists), task creation triggered
- **When:** User record is created, then cohort assignment runs
- **Then:** 
  - User record created successfully
  - Cohort assigned correctly based on current week
  - Database reflects correct cohort values
- **Test Data:** Configure `launchDate` to put current date in specific week range
- **Justification:** Multi-component integration (taskStore → user creation → cohort assignment → database)

**4.1-INT-005: Cohort Assignment - OnboardingScreen Integration (Integration, P0)**
- **Description:** Test cohort assignment when user is created via OnboardingScreen
- **Given:** New user completes onboarding
- **When:** User record is created, then cohort assignment runs
- **Then:** Cohort assigned correctly, user can proceed to main screen
- **Test Data:** Same as INT-004
- **Justification:** Multi-component integration (onboarding → user creation → cohort assignment)

**4.1-INT-006: Cohort Assignment - SettingsScreen Integration (Integration, P0)**
- **Description:** Test cohort assignment when user is created via SettingsScreen (test email)
- **Given:** New user, no user record, test email triggered
- **When:** User record is created, then cohort assignment runs
- **Then:** Cohort assigned correctly
- **Test Data:** Same as INT-004
- **Justification:** Multi-component integration (settings → user creation → cohort assignment)

**4.1-INT-007: Idempotency Check (Integration, P1)**
- **Description:** Test that cohort assignment doesn't overwrite existing assignment
- **Given:** User with `cohort = 'early_freemium_2.99'` (already assigned)
- **When:** User creation logic runs again (e.g., task creation)
- **Then:** 
  - Idempotency check detects existing cohort
  - Cohort assignment is skipped
  - User record retains original cohort value
- **Test Data:** User with non-default cohort value
- **Justification:** Data integrity protection, prevents overwriting

**4.1-E2E-001: Complete Signup Flow with Cohort Assignment (E2E, P0)**
- **Description:** Test full user signup journey with cohort assignment verification
- **Given:** New user, app configured with `launchDate`
- **When:** 
  1. User signs up via magic link
  2. User authenticates
  3. User completes onboarding (or creates first task)
  4. User record created
  5. Cohort assigned
- **Then:** 
  - User successfully signed up
  - Cohort assigned correctly in database
  - User can use app normally
- **Test Data:** Configure `launchDate` for specific week range
- **Justification:** Critical user journey, validates end-to-end flow

### AC4: Verify Cohort Saved Correctly

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.1-UNIT-009 | Unit | P1 | Test date conversion to ISO string for Supabase | Pure data transformation |
| 4.1-E2E-002 | E2E | P1 | Manual verification: Signup multiple users, verify cohorts in database | Critical validation |

**4.1-UNIT-009: Date to ISO String Conversion (Unit, P1)**
- **Description:** Test that Date objects are correctly converted to ISO strings for Supabase
- **Given:** Date object (e.g., `new Date(Date.now() + 30 * 24 * 60 * 60 * 1000)`)
- **When:** Convert to ISO string: `date.toISOString()`
- **Then:** Returns valid ISO 8601 string (e.g., `"2025-02-11T12:00:00.000Z"`)
- **Justification:** Pure data transformation, ensures Supabase compatibility

**4.1-E2E-002: Manual Database Verification (E2E, P1)**
- **Description:** Manual test: Sign up multiple users across different week ranges, verify cohorts in Supabase Dashboard
- **Given:** Multiple test users signed up
- **When:** Query Supabase Dashboard → users table
- **Then:** 
  - Each user's `cohort` matches expected value for their signup week
  - `grandfather_status` is correct
  - `trial_started_at` and `trial_expires_at` are set correctly (or null for grandfathered users)
  - Weeks 7-8 users show roughly 50/50 split between 2.99 and 4.99 cohorts
- **Test Data:** 
  - Configure `launchDate` to test different week ranges
  - Sign up 5-10 test users per week range
- **Justification:** Final validation, ensures production-ready behavior

## Test Environment Requirements

### Unit Tests
- **Environment:** Local development (Node.js/Jest)
- **Dependencies:** None (pure functions)
- **Setup:** Mock date functions, mock Math.random

### Integration Tests
- **Environment:** Local with Supabase connection (or test Supabase instance)
- **Dependencies:** Supabase client, Expo Constants
- **Setup:** Test database with users table, configured `app.json`

### E2E Tests
- **Environment:** Development/staging environment
- **Dependencies:** Full app stack
- **Setup:** Configured `app.json` with test `launchDate`, test Supabase instance

## Test Implementation Recommendations

### Unit Test Framework
- **Framework:** Jest (standard for React Native/TypeScript)
- **Location:** `src/lib/__tests__/cohortAssignment.test.ts`
- **Pattern:** Pure function testing with mocked dependencies

### Integration Test Framework
- **Framework:** Jest with Supabase test client
- **Location:** `__tests__/integration/cohortAssignment.test.ts`
- **Pattern:** Real Supabase connection, cleanup after tests

### E2E Test Framework
- **Framework:** Manual testing (appropriate for MVP)
- **Future:** Consider Detox or Appium for automated E2E (future enhancement)
- **Pattern:** Manual signup flows, database verification
