**Users Table Monetization Fields:**
- `cohort VARCHAR(50) NOT NULL DEFAULT 'free_launch' CHECK (cohort IN ('free_launch', 'early_freemium_2.99', 'early_freemium_4.99', 'paid_cohort_v1', 'paid_cohort_v2'))`

  - **Current Strategy (Free Until Traction):** All users get `'free_launch'` during launch period
  - **Future Cohorts (When monetization re-enabled):** `'early_freemium_2.99'`, `'early_freemium_4.99'`, `'paid_cohort_v1'`, `'paid_cohort_v2'` reserved for future use

  - **Current Strategy:** All users get `grandfather_status = true` (free forever during launch)
  - **Future:** Will vary based on signup timing when tiered monetization re-enabled
- `trial_started_at TIMESTAMP DEFAULT NULL`
  - **Current Strategy:** Always `null` (no trials during free launch)
  - **Future:** Will be set to `NOW()` when user starts trial (when monetization re-enabled)
- `trial_expires_at TIMESTAMP DEFAULT NULL`
  - **Current Strategy:** Always `null` (no trials during free launch)
  - **Future:** Will be set to `NOW() + 30 days` when user starts trial (when monetization re-enabled)

**RLS Policies:**
- Users can update their own records: `users_update_own` policy exists
- Cohort assignment will use authenticated user's session to update their record

### Technical Constraints

**Week Calculation Logic:**
- Weeks are calculated from `LAUNCH_DATE` to current date (function preserved for future use)
- **Current Strategy:** Week calculation is not used - all users get same assignment regardless of week
- **Future Use:** Original week-based logic preserved in comments:
  - Week 1 = days 0-6 since launch
  - Week 2 = days 7-13 since launch
  - Week 3 = days 14-20 since launch
  - Week 4 = days 21-27 since launch
  - Week 5 = days 28-34 since launch
  - Week 6 = days 35-41 since launch
  - Week 7 = days 42-48 since launch
  - Week 8 = days 49-55 since launch
  - Week 9 = days 56+ since launch

**Random Split Logic (Weeks 7-8):**
- Use `Math.random() < 0.5` for 50/50 split
- This ensures roughly equal distribution between `'early_freemium_2.99'` and `'early_freemium_4.99'`
- Random split happens at assignment time (not deterministic based on user ID)

**Date/Time Handling:**
- All dates should use UTC to avoid timezone issues
- JavaScript `Date.now()` returns milliseconds since epoch (UTC)
- Supabase TIMESTAMP fields store UTC timestamps
- Convert JavaScript dates to ISO strings: `date.toISOString()`

**Environment Variable Configuration:**
- `launchDate` should be set in `app.json` `extra` field (use camelCase key name, matching Story 1.2 pattern)
- Access via: `Constants.expoConfig?.extra?.launchDate` (camelCase, consistent with `supabaseUrl` and `supabaseAnonKey` access pattern)
- Example `app.json` configuration:
  ```json

      "launchDate": "2025-01-01T00:00:00Z"
    }
  }
  ```
- Format: ISO date string (e.g., `"2025-01-01T00:00:00Z"`)
- For development: Can set to past date to test different week ranges
- For production: Must be set to actual launch date
