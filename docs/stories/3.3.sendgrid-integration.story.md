### Supabase Edge Function Architecture
[Source: docs/architecture/email-delivery-system.md Section: Supabase Edge Function Implementation]

**Edge Function Structure:**
- Functions are written in TypeScript/Deno runtime
- Each function lives in `supabase/functions/{function-name}/` directory
- Main entry point: `index.ts` in function directory
- Functions use `Deno.serve()` handler pattern
- Functions can read environment variables via `Deno.env.get()`

**Edge Function Request/Response Pattern:**
[Source: Supabase Edge Functions documentation, architecture examples]

```typescript
Deno.serve(async (req: Request) => {
  // Parse request
  const { to, subject, html } = await req.json()
  
  // Process request
  // ...
  
  // Return response
  return new Response(JSON.stringify({ success: true }), {
    headers: { 'Content-Type': 'application/json' }
  })
})
```

**Environment Variables/Secrets:**
[Source: docs/architecture/deployment-strategy.md]

- Edge Functions use Supabase secrets management for API keys
- Secrets are configured via Supabase dashboard or CLI
- Access secrets in code: `Deno.env.get('SECRET_NAME')`
- Never commit secrets to code or version control

**Edge Function Authentication & Security:**
[Source: docs/architecture/email-delivery-system.md Lines 343-361, Supabase Edge Functions documentation]

**For Story 3.3 (MVP Testing):**
- Function can be invoked using Supabase anon key: `Authorization: Bearer <anon-key>`
- Anon key provides public access for testing purposes
- Function URL format: `https://<project>.supabase.co/functions/v1/send-email`

**For Production (Story 3.5 - Automated Cron):**

- Edge Function secrets are configured in Supabase dashboard
- More secure than anon key for scheduled jobs

**Security Considerations:**
- For MVP (Story 3.3), anon key access is acceptable for manual testing
- Function validates input (email format, required fields) to prevent abuse
- In Story 3.5, automated cron will use proper edge function secret authentication
- Function logs requests for monitoring (Supabase Edge Functions dashboard)
- **Note:** Story 3.3 focuses on basic functionality; authentication hardening can be enhanced in future stories if abuse becomes a concern

### SendGrid API Integration
[Source: docs/architecture/email-delivery-system.md Lines 204-230]

**SendGrid API Endpoint:**
- URL: `https://api.sendgrid.com/v3/mail/send`
- Method: `POST`
- Authentication: Bearer token in `Authorization` header
- Content-Type: `application/json`

**SendGrid Request Format:**
[Source: docs/architecture/email-delivery-system.md Lines 210-222]

```typescript
{
  personalizations: [{ to: [{ email: to }] }],
  from: { email: SENDGRID_FROM_EMAIL, name: 'TodoTomorrow' },
  subject: subject,
  content: [{ type: 'text/html', value: html }],
  mail_settings: {
    sandbox_mode: { enable: false }
  }
}
```

**SendGrid Response:**
- Success: HTTP 202 Accepted (SendGrid accepts email for delivery)
- Response headers include `x-message-id` for tracking
- Error: HTTP 4xx/5xx with error details in response body

**SendGrid Free Tier:**
[Source: docs/architecture/email-delivery-system.md Lines 384-387]

- Free tier: 100 emails/day
- Sufficient for MVP with small user base
- Monitor usage and upgrade to paid tier ($20/month ~ 500K/month) as needed

**SendGrid Configuration:**
[Source: docs/architecture/email-delivery-system.md Lines 366-369]

**For MVP (Story 3.3):**
- Create free SendGrid account
- Verify single sender email (can use temp email for MVP)
- Generate API key for Edge Function use

**Post-MVP (Future Enhancement):**
- Verify sender domain (DNS DKIM/SPF records)
- Enable SPF, DKIM, DMARC authentication
- Warm up sending gradually
