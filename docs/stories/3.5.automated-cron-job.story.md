# Story 3.5: Automated Cron Job

## Status
Approved

## Story
**As a** user  
**I want to** automatically receive my task list every morning  
**So that** I don't have to manually send it

## Acceptance Criteria
1. Supabase cron job created (runs hourly via pg_cron at minute 0 of each hour)
2. Query users: WHERE delivery_time converts to current UTC hour in their timezone AND (is_paid = true OR trial is valid) AND last_email_sent_at < 20 hours ago
3. For each user: Query tasks based on workflow_mode (fresh_start: created_at > last_email_sent_at AND status = 'open', carry_over: status = 'open')
4. Send email even if user has no tasks (empty state email: "No new tasks for today. Enjoy your morning coffee! ☕")
5. Generate email HTML from template, send via Resend API
6. Update: `last_email_sent_at = NOW()` after successful send
7. Log email send in email_logs table
8. Test: Set delivery_time to current time + 1 hour → Wait → Receive email

### Timezone Conversion Logic
[Source: docs/architecture/email-delivery-system.md Lines 31-69]

**Problem:** User sets "6:00 AM EST" locally. Cron job runs in UTC. Need to match user's local hour.

**Solution:** Use PostgreSQL timezone conversion in SQL query:
- Store timezone as IANA string (e.g., "America/New_York") in users table
- Use `NOW() AT TIME ZONE u.timezone` to convert UTC to user's local time
- Compare `EXTRACT(HOUR FROM (NOW() AT TIME ZONE u.timezone))` with `EXTRACT(HOUR FROM u.delivery_time)`

**SQL Query Pattern:**
[Source: docs/architecture/email-delivery-system.md Lines 37-66]

```sql
SELECT 
  u.id,
  u.email,
  u.delivery_time,
  u.timezone,
  u.workflow_mode,
  u.last_email_sent_at
FROM users u
WHERE 
  u.deleted_at IS NULL
  AND (u.is_paid = true OR (
    u.trial_started_at IS NOT NULL 
    AND u.trial_started_at > NOW() - INTERVAL '30 days'
    AND u.trial_tasks_count < 100
  ))
  AND EXTRACT(HOUR FROM (NOW() AT TIME ZONE u.timezone))::INT = 
      EXTRACT(HOUR FROM u.delivery_time)::INT
  AND (
    u.last_email_sent_at IS NULL 
    OR u.last_email_sent_at < NOW() - INTERVAL '20 hours'
  )
ORDER BY u.id;
```

**Why 20 hours instead of 24h:** Accounts for cron variance (hourly job), prevents double-sends if job runs slightly early/late.

**Timezone Conversion in Supabase:**
- Supabase PostgreSQL supports `AT TIME ZONE` syntax
- Can use `.rpc()` for custom SQL functions, or use `.select()` with raw SQL
- **For MVP (PM Recommendation):** Use Option B (JavaScript filter) for simplicity - fetch eligible users, filter by timezone in code
- **For Scale (Future Enhancement):** Consider Option A (PostgreSQL function via `.rpc()`) for better performance with larger user bases

### Task Querying by Workflow Mode
[Source: docs/architecture/email-delivery-system.md Lines 115-136]

**Fresh Start Mode:**
- Only send tasks created since last email
- Query: `tasks WHERE user_id = ? AND status = 'open' AND created_at > last_email_sent_at`
- Logic: User wants fresh start each day, only new tasks since last email

**Carry Over Mode:**
- Send all open tasks (persistent task list)
- Query: `tasks WHERE user_id = ? AND status = 'open'`
- Logic: User wants to see all incomplete tasks, regardless of when created
- **Note:** Architecture diagram shows `status IN ('open', 'completed')` but implementation code uses only `status = 'open'` - follow implementation code (only open tasks)

**Implementation:**
```typescript
let query = supabase
  .from('tasks')
  .select('id, text, priority, due_date, created_at')
  .eq('user_id', userId)
  .eq('status', 'open')

if (workflowMode === 'fresh_start' && lastEmailSentAt) {
  query = query.gt('created_at', lastEmailSentAt)
}
// carry_over: query already filters status = 'open'

const { data, error } = await query.order('created_at', { ascending: false })
```

### Resend API Integration
[Source: Story 3.3 Dev Notes, docs/architecture/email-delivery-system.md Lines 204-236]

**Resend API Endpoint:**
- URL: `https://api.resend.com/emails`
- Method: `POST`
- Authentication: Bearer token in `Authorization` header
- Content-Type: `application/json`

**Resend Request Format:**
```typescript
{
  from: RESEND_FROM_EMAIL,
  to: [userEmail],
  subject: subject,
  html: html
}
```

**Resend Response:**
- Success: HTTP 200 OK with JSON body containing `{ id: 'message-id', ... }`
- Message ID is in response body `id` field (not header)
- Error: HTTP 4xx/5xx with error details in JSON response body

**Implementation Pattern:**
```typescript
const response = await fetch('https://api.resend.com/emails', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${RESEND_API_KEY}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    from: RESEND_FROM_EMAIL,
    to: [userEmail],
    subject,
    html
  })
})

if (!response.ok) {
  const error = await response.json()
  throw new Error(`Resend API error: ${JSON.stringify(error)}`)
}

const data = await response.json()
return data.id || null // message ID
```

```sql
CREATE TABLE email_logs (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  recipient_email VARCHAR(255) NOT NULL,
  subject VARCHAR(255) NOT NULL,
  resend_message_id VARCHAR(255) UNIQUE DEFAULT NULL,

  status VARCHAR(20) NOT NULL DEFAULT 'sent'

  created_at TIMESTAMP DEFAULT NOW()
);
```

### Supabase pg_cron Configuration
[Source: docs/architecture/email-delivery-system.md Lines 345-368]

**Cron Job Setup:**
- pg_cron extension must be enabled (done in database migrations)
- Schedule job using `cron.schedule()` function
- Job runs Edge Function via `http_post()` function
- Use Edge Function secret for authentication (not anon key)

**Cron Schedule Pattern:**
- `'0 * * * *'` - Every hour at minute 0 (1:00, 2:00, 3:00, etc.)
- Hourly execution ensures timezone conversions work correctly

**Cron Job SQL:**
```sql
SELECT cron.schedule(
  'send-daily-emails-hourly',
  '0 * * * *', -- every hour
  $$
  SELECT http_post(
    'https://<project>.supabase.co/functions/v1/send-daily-emails',
    '{}',
    'Bearer <edge-function-secret>'
  )
  $$
);
```

**Edge Function Secret:**
- Configure in Supabase dashboard: Settings > Edge Functions > Secrets
- Or use `supabase secrets set EDGE_FUNCTION_SECRET=<value>`
- Use this secret in cron job `http_post()` call for authentication

**Viewing Active Jobs:**
```sql
SELECT * FROM cron.job WHERE jobname = 'send-daily-emails-hourly';
```

**Deleting Job (if needed):**

### Error Handling & Failure Tracking
[Source: docs/architecture/email-delivery-system.md Lines 264-274, 384-389]

**User Failure Tracking:**
- Track `consecutive_failures` in users table
- Update `last_email_failed_at` on failure
- Increment `consecutive_failures` on failure
- Reset `consecutive_failures` to 0 on success

**Failure Update Pattern:**
[Source: docs/architecture/email-delivery-system.md Lines 270-280]

```typescript
await supabase
  .from('users')
  .update({ 
    last_email_failed_at: new Date().toISOString(),
    consecutive_failures: supabase.raw('consecutive_failures + 1')
  })
  .eq('id', userId)
```

**Note:** Supabase query builder may require using `supabase.rpc()` for incrementing integers, or fetching current value and updating. Verify Supabase.js API supports `.raw()` or use alternative approach.

**Batch Processing:**

### Refactoring Performed

**File**: `supabase/functions/send-daily-emails/index.ts`

**Change**: Moved template file reading outside user processing loop (lines 195-218)

**Why**: Performance optimization - template was being read once per user in the loop, causing unnecessary I/O operations. For a batch of 100 users, this would read the template file 100 times.

**How**: Template is now read once before processing users, then reused for all users in the batch. This reduces I/O operations from O(n) to O(1) where n is the number of eligible users.
