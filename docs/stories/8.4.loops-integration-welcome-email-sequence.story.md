# Story 8.4: Loops Integration & Welcome Email Sequence

## Status
❌ **DEFERRED / ABANDONED** - Permanently deferred due to excessive complexity (2025-11-12)

**Decision:** Loops integration is **permanently deferred**. The complexity (database triggers, Edge Functions, pg_net issues, multiple migrations) far exceeds the value for launch. Welcome emails are not critical and can be implemented via simpler alternatives post-launch when we have real users.

**Deferral Date:** 2025-11-12  
**Reason:** Too many errors, too many issues, excessive complexity for a "nice-to-have" feature. Will explore simpler alternatives after launch when we have users and can justify the effort.

**Alternative Approaches for Future:**
- Send welcome email directly from app code (10 lines vs. database infrastructure)
- Use Supabase Auth webhooks instead of database triggers
- Use Resend transactional emails (already integrated)
- Implement only when we have plenty of users requesting it

**Rollback Status:** ✅ Complete - All Loops code, migrations, and dashboard items removed. See `8.4.ROLLBACK-loops-integration-rollback-plan.story.md` for details.

## Epic Context
**Epic 8: Sentry Crash Logging, PostHog Analytics & Loops Email Sequences - Post-Launch Enhancement**
This story is part of Epic 8, a post-launch epic focused on integrating Sentry for crash logging, PostHog for product analytics, and Loops for automated email sequences. This story implements Loops integration for automated welcome email sequences to improve user engagement and onboarding.

**Dependencies:** Story 8.1 (Sentry Setup) must be complete. Loops is independent of PostHog, only needs app to be launched.

## Dev Notes

### Previous Story Insights
[Source: docs/stories/8.3.posthog-event-tracking-implementation.story.md]

**Key Patterns from Story 8.3 (PostHog Event Tracking):**
1. **Edge Function Structure**: Edge Functions use Deno runtime with TypeScript
   - Use `Deno.serve()` for HTTP handler
   - Use `Deno.env.get()` for environment variables
   - Use native `fetch()` for HTTP API calls (no need for external HTTP libraries)
   - Pattern: `supabase/functions/{function-name}/index.ts`

2. **External API Integration Pattern**:
   - PostHog HTTP API integration used `fetch()` with proper headers
   - Error handling: API failures don't break main functionality
   - Logging: Comprehensive console.log statements for debugging
   - Pattern: Try-catch around API calls, log errors, return success even on failure

3. **Database Trigger Pattern**:
   - Database triggers can call Edge Functions via `net.http_post()`
   - Use `PERFORM` for async calls (non-blocking)
   - Triggers should not block the main operation (user signup)
   - Pattern: Trigger fires AFTER INSERT, calls Edge Function webhook

4. **Environment Variables**:
   - Supabase secrets stored in dashboard: Settings → Edge Functions → Secrets
   - Accessed in Edge Functions via `Deno.env.get('SECRET_NAME')`
   - Pattern: Check for secret existence, log warning if missing, handle gracefully

### Loops API Integration Details
[Source: docs/prd/epic-8-posthog-loops-integration.md]

**Loops API Endpoint:**
[Source: https://loops.so/docs/transactional]
- Base URL: `https://app.loops.so/api`
- Transactional email endpoint: `POST https://app.loops.so/api/v1/transactional`
- Authentication: Bearer token in `Authorization` header
- API Key: Obtained from Loops dashboard (Settings → API → Generate key)
- **Verified:** Endpoint confirmed from Loops transactional email documentation

**Loops API Request Format:**
[Source: https://loops.so/docs/transactional]
```json
{
  "transactionalId": "cmhw2qu2j07i94l0is7v0033v",
  "email": "user@example.com",
  "dataVariables": {
    "name": "John",
    "customField": "value"
  }
}
```
- `transactionalId`: Template ID from Loops dashboard (required) - Get from template's "Publish" page
- `email`: User's email address (required)
- `dataVariables`: Optional object with dynamic data for email personalization
- **Template IDs Configured:**
  - Welcome email: `cmhw2qu2j07i94l0is7v0033v`
  - Day 3 "no tasks": `cmhvyaekx3ttwwq0i7b9ewfq7`
  - Day 5 inactivity: `cmhw3sebk0bqf760ipe4mvthm`

**Loops API Response:**
- Success: `{ "success": true }`
- Error: `{ "success": false, "message": "error message" }`
- Rate limiting: HTTP 429 with `x-ratelimit-limit` and `x-ratelimit-remaining` headers (10 requests per second limit)

**Loops Scheduling:**
- Welcome email sent immediately via database trigger (on user signup)
- Day 3 "no tasks" email sent via cron job (checks users who signed up 3 days ago with 0 tasks)
- Day 5 inactivity email sent via cron job (checks users with no activity in last 5 days)
- Cron job approach gives more control over conditions (e.g., only send if no tasks)

**Database Queries for Scheduled Emails:**
- Day 3 "no tasks" query:
  ```sql
  SELECT u.id, u.email
  FROM users u
  WHERE u.created_at::date = (CURRENT_DATE - INTERVAL '3 days')::date
    AND u.deleted_at IS NULL
    AND NOT EXISTS (
      SELECT 1 FROM tasks t
      WHERE t.user_id = u.id
        AND t.deleted_at IS NULL
    )
    -- Optional: Add check to prevent duplicate sends
    -- AND (u.last_day3_email_sent_at IS NULL OR u.last_day3_email_sent_at < u.created_at + INTERVAL '3 days')
  ```
- Day 5 inactivity query (using `last_active_at` if available, otherwise `updated_at`):
  ```sql
  SELECT u.id, u.email
  FROM users u
  WHERE (u.last_active_at IS NOT NULL AND u.last_active_at < NOW() - INTERVAL '5 days')
     OR (u.last_active_at IS NULL AND u.updated_at < NOW() - INTERVAL '5 days')
    AND u.deleted_at IS NULL
    AND u.created_at < NOW() - INTERVAL '5 days'  -- User must exist for at least 5 days
    -- Optional: Add check to prevent duplicate sends
    -- AND (u.last_day5_email_sent_at IS NULL OR u.last_day5_email_sent_at < NOW() - INTERVAL '5 days')
  ```

**Duplicate Email Prevention:**
- Option 1: Track email sends in `users` table (add `last_day3_email_sent_at`, `last_day5_email_sent_at` fields)
- Option 2: Query Loops API to check if email was already sent (more complex, requires API call)
- Option 3: Use Loops' built-in duplicate prevention if available
- Recommended: Option 1 (database fields) for simplicity and reliability

### Database Trigger Approach
[Source: docs/prd/epic-8-posthog-loops-integration.md]

**Recommended Approach:** Database trigger (simpler, more reliable than app-level triggers)

**Trigger Function Pattern:**
```sql
CREATE OR REPLACE FUNCTION trigger_loops_welcome()
RETURNS TRIGGER AS $$
BEGIN
  PERFORM net.http_post(
    url := 'https://[PROJECT_REF].supabase.co/functions/v1/trigger-loops-welcome',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer [ANON_KEY]'
    ),
    body := jsonb_build_object(
      'user_id', NEW.id,
      'email', NEW.email
    )
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER on_user_signup_trigger_loops
  AFTER INSERT ON users
  FOR EACH ROW
  EXECUTE FUNCTION trigger_loops_welcome();
```

**Important Notes:**
- Use `PERFORM` for async calls (non-blocking)
- Use `net.http_post()` with schema prefix (not `http_post()`)
- Use `jsonb_build_object()` for JSON body
- Trigger fires AFTER INSERT (not BEFORE) to ensure user record exists
- Return NEW to allow INSERT to proceed
